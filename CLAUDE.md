# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — run the bot locally with `node --watch` (needs Mongo on `MONGO_URI`, default `mongodb://localhost:27017`).
- `npm start` — run without watch.
- `npm test` — run the full Vitest suite once (`vitest run`).
- `npx vitest run tests/beats.test.js` — run a single test file.
- `npx vitest run -t "createBeat"` — run a single test by name.
- `npm run build:web` — build the React/Vite SPA into `web/dist/`. The Express server serves it at `/` when present.
- `npm run dev:web` — run the Vite dev server (port 5173) with `/api`, `/auth`, `/image`, `/attachment`, `/pdf` proxied to the Express server on 3000.
- `docker compose up --build -d` — production-style run (bot + Mongo).

`tests/setup.js` (loaded via `vitest.config.js`) populates the env vars `src/config.js` requires, so tests can be run without a real `.env`.

## Architecture

Discord bot + collaborative editor SPA in one Node process: every non-bot message in `MOVIE_CHANNEL_ID` triggers an agentic loop that mutates screenplay state in MongoDB; the same state is editable in the browser by anyone the channel has approved. The Express server (`src/server/index.js`, `WEB_PORT` default 3000) hosts both the SPA (`web/dist/`) and the read endpoints (`GET /health`, `GET /pdf/:filename`, `GET /image/:fileId`, `GET /attachment/:fileId`) plus the new `/auth/*` and `/api/*` REST endpoints. A separate Hocuspocus WebSocket server (`HOCUSPOCUS_PORT` default 3001) handles y-doc sync. URLs use `WEB_PUBLIC_BASE_URL` when set.

### Multi-project

- `projects` collection: `{ _id: ObjectId, title, title_lower, created_at }` (`src/mongo/projects.js`). Titles are plain text: trimmed, non-empty, max 120 chars, no `/`; `title_lower` has a unique index. The **default project** is the oldest by `created_at`; `getDefaultProject()` lazily creates one titled "Screenplay" on an empty collection.
- **`project_id` convention**: stored as a 24-hex *string* (`projects._id.toString()`) on every content doc (`plots`, `characters`, `messages`, `dialogs`, `video_scenes`, `video_prompts`, the composite `prompts` ids) and in GridFS `metadata.project_id`. Every project-scoped helper in `src/mongo/*` takes `projectId` as its first parameter (or as an options key on single-options-object helpers) and **throws `projectId required`** on a falsy value — a throw means a missed threading site; fix the caller, never re-add a default. ObjectId-addressed lookups locate by id, then verify the doc's `project_id`; mismatches behave as not-found (this is what makes stale entity ids from pre-switch chat history fail safely).
- **Agent**: the channel's active project lives in `channel_state.current_project_id`; `handleMessage` resolves it inside the per-channel mutex and threads `{projectId, projectTitle}` through the agent `context` (passed by `dispatchTool` to all handlers). The lazy-loaded `set_project` tool (input `{title}`) switches it, mutates the context in place for later same-turn calls, and — via the `set_` mutating prefix — forces a system-prompt rebuild. Project creation is web-only.
- **REST**: `src/web/projectMiddleware.js#resolveProject()` reads the `X-Project-Id` header (`?project_id=` query fallback for SSE, since `EventSource` can't set headers) into `req.projectId`/`req.projectTitle`; missing → default project, unknown id → 404 `{error:'unknown project'}`. `GET /api/projects` lists, `POST /api/projects {title}` creates (201; 400 invalid title, 409 duplicate), `PATCH /api/projects/:id {title}` renames (400/404/409), `DELETE /api/projects/:id` fully deletes one project (404 unknown, **409 when it's the last project**), `GET /api/info` additionally returns `project_id`/`project_title`. The `/projects*` paths are exempt from `resolveProject()` — they address a project by path id, so a stale `X-Project-Id` can't misdirect them.
- **Delete cascade** (`src/web/projectDelete.js#deleteProjectCascade`): collect beat/character/set ids → delete `plots`/`characters`/`sets`/`messages`/`dialogs`/`video_prompts`/`video_scenes`/`edit_announcements` (and any legacy `storyboards` rows) by `project_id` → the three composite `prompts` ids → GridFS `images`/`attachments` files+chunks by `metadata.project_id` → `yjs_docs` rows for the project's singleton and entity rooms → Chroma chunks (best-effort) → repoint any `channel_state.current_project_id` at the default project → the `projects` doc **last** (a mid-cascade crash leaves the project visible and re-deletable). `token_usage` is channel-scoped and deliberately untouched. Renaming is title-only — every room, file, and row keys off `project_id`. Both are surfaced on the About page (`web/src/widgets/ProjectSettings.jsx`); delete requires typing the project title.
- **SPA**: all routes nest under `/p/:projectTitle/*`; legacy paths redirect into the viewer's last-used project (localStorage key `screenplay_project_v1`). `web/src/project/ProjectContext.jsx` resolves the title and primes the module-level store in `web/src/api.js` (`setCurrentProject` → `authHeaders()` adds `X-Project-Id`, `apiSseUrl()` appends `project_id`). Switching projects is a full-page `location.assign` to the new `/p/<title>/` URL.
- **Migration runbook** (one-shot, idempotent; also applies when restoring a pre-multi-project dump). MIGRATE BEFORE RESTART: a restarted bot on the new code lazily creates a "Screenplay" project (and seeds fresh default templates) on its first request, which the migration would then have to rename and overwrite. The source is bind-mounted (`./src`, `./scripts` → `/app/...`), so new code ships without a restart and runs via `docker compose exec` while the old process keeps executing the old code: 0) `mongodump` first — it is the only rollback, 1) rsync the new source to the host WITHOUT restarting (deploy.sh's rsync line, minus its `docker compose up -d bot && docker compose restart bot` tail — do NOT run plain `./deploy.sh` for this first multi-project deploy; it always restarts right after rsync), 2) `ssh <host> 'cd <dir> && docker compose exec bot node scripts/migrate-multi-project.js'` (the exec'd process is NEW code via the mount; creates the default project titled from the screenplay title, stamps `project_id` everywhere, re-keys `prompts` — legacy customized templates overwrite any freshly-seeded defaults — renames the three singleton y-doc rooms preserving CRDT state, ensures the plots/characters indexes, points `channel_state` at the default project), 3) `ssh <host> 'cd <dir> && docker compose exec bot node scripts/reindex-rag.js'` (full Chroma reindex with `project_id` metadata), 4) `ssh <host> 'cd <dir> && docker compose up -d bot && docker compose restart bot'` — only now does the bot load the new code, against fully-migrated data, 5) re-run `docker compose exec bot node scripts/migrate-multi-project.js` once after the restart — it is idempotent and sweeps any messages the old bot wrote between the stamping pass and the restart. Subsequent deploys go back to plain `./deploy.sh`. Once a migrated deployment is verified, the read-side leniency toward unstamped legacy rows (characters/storyboards/dialogs/GridFS listers) can be retired in a future cleanup pass. Backup/restore remains whole-DB (`mongodump` / `mongorestore --drop`): restoring to fix project A rolls back every other project too — no per-project backup or export in v1.

### Users & permissions

- **Master switch**: the whole permission system is active iff `ADMIN_USERNAME` is set (live getter `config.web.adminUsername`; `tests/setup.js` pins it to `''` so the suite always runs in legacy open mode — permission tests set the env var per-case). Unset = legacy behavior: every session sees/edits every project. The admin is the session whose username matches the env var case-insensitively (`isAdmin` in `src/web/permissions.js`); admin-ness is derived at request time, never stored.
- **`users` collection** (`src/mongo/users.js`): one doc per human — `{name (first-seen display casing), name_lower (unique), project_ids: [24-hex], last_granted_by}`. Same login name in any casing = same account; `approveAuthRequest` find-or-creates the user, stamps `user_id` on the session, and gives the session the canonical casing. `project_ids` is always replaced wholesale (set semantics; never `$addToSet` — the fake Mongo lacks it).
- **Enforcement points** (all in new modules — see the mocked-test constraint below): `requireProjectAccess()` mounted right after `requireSession()` in `entityRoutes.js` (403 `{error:'forbidden project'}`; also covers `resolveProject`'s default-project fallback, which fails closed); `GET /api/projects` returns `listProjectsFor(username)` — the SPA treats this list as its authorization oracle; `POST/PATCH/DELETE /projects*` carry `requireAdmin()`; Hocuspocus `onAuthenticate` calls `assertRoomAccess` (browser websockets only — the bot/gateway uses `openDirectConnection`, which never runs `onAuthenticate`). The four pre-auth SSE routes stay capability-keyed by unguessable job ids; public file URLs (`/image`, `/attachment`, `/pdf`) stay public (Discord embeds depend on them).
- **CRITICAL test constraint**: ~30 test files replace `src/web/auth.js` wholesale via `vi.mock(..., () => ({ requireSession: ... }))`. Never add an export to `src/web/auth.js` that `entityRoutes.js` imports — new middleware goes in `src/web/permissions.js` / `src/web/adminRoutes.js`.
- **Grant flows**: after an Approve in Discord, the bot follows up with a `StringSelectMenu` (`src/discord/grantMenu.js`, custom_id `perm:grant:<user _id>`) listing all projects (25-option Discord cap) — anyone in the channel sets the user's exact granted set; the same message stays re-adjustable. The SPA Admin page (`web/src/routes/Admin.jsx`, admin-only link before About in the header) does the same via `GET /api/admin/users` + `PUT /api/admin/users/:id/projects` (`/admin*` is exempt from `resolveProject`, like `/projects*`). Project delete cascade pulls the id from every user's grants.
- **SPA session flag**: `/auth/validate` and `/auth/status` return `is_admin` + `permissions_enabled`; `canManageProjects(session)` (`web/src/auth/session.js`) gates create/rename/delete UI so legacy open mode keeps them visible for everyone. A 403 `forbidden project` in `api.js#check()` clears the stored project and bounces to the app root (handles stale-localStorage/revoked-mid-session).
- **Migration** (`scripts/migrate-users.js`, idempotent): grandfathers every existing session name into a user granted ALL current projects and links sessions; never touches existing user docs (a narrowed grant set is never re-widened). Deploy order: rsync new code → `docker compose exec bot node scripts/migrate-users.js` → add `ADMIN_USERNAME` to `.env` → restart.

### Collaborative editor (SPA)

`src/web/` is the backend half; `web/` is the React/Vite SPA.

- **Auth**: visitors enter a name → `POST /auth/request` posts an embed with Approve/Deny buttons in `MOVIE_CHANNEL_ID` → click handler in `src/discord/interactions.js` updates the `auth_requests` doc → SPA polls `/auth/status` until approved → server returns a `session_id` stored in `localStorage` permanently. No revocation in v1; sessions never expire. Approval find-or-creates the `users` doc (see Users & permissions above).
- **Mutation gateway** (`src/web/gateway.js`): single writer for editable entities. The agent loop's tool handlers AND the SPA's REST endpoints both route through it. For text fields it opens a server-side direct connection to the entity's y-doc (via Hocuspocus) and applies edits as CRDT operations through a headless Tiptap editor (`src/web/headlessEditor.js`, runs Tiptap on Node via JSDOM). For non-text mutations (image add/remove, set main, plays_self toggle, etc.) it writes Mongo and broadcasts a stateless `{type:'fields_updated'}` ping to the room so connected SPAs re-render the affected widgets.
- **Bot as collaborator**: when the bot mutates a text field, the gateway briefly sets the room's awareness with the bot's Discord display name and a fixed color (`config.web.botColor`), so connected humans see the bot's caret in the field it's editing. Awareness is cleared once the mutation finishes.
- **Save model**: no Save button. Hocuspocus persists y-doc binary state to the `yjs_docs` collection on every store tick (~2s debounced). The same hook also renders each text fragment to markdown and writes it to the corresponding Mongo entity field via `src/web/roomRegistry.js`. The bot reads from Mongo at the start of each agent iteration, so it sees at most ~2s stale text — acceptable.
- **Creating rows with text** (`createVideoPromptViaGateway`, `createVideoSceneViaGateway`, `createDialogViaGateway`): pre-generate the `_id`, seed the room fragments (`seedNewRowFragments`), THEN insert the Mongo row carrying the same text. Inserting first lets a store tick see the row with empty fragments and write `''` over its text.
- **Gateway fallback**: when Hocuspocus isn't running (tests, CLI scripts), text-mutation gateway calls fall back to writing Mongo directly via the existing helpers (`isHocuspocusRunning()` check). This keeps the test suite working without spinning up a real WebSocket server.
- **Names are markdown**: every text field — including character `name` and `hollywood_actor` — uses the full Tiptap toolkit. `name_lower` is recomputed from `stripMarkdown(name)` so case-insensitive lookups still work (`src/util/markdown.js`). Discord renders markdown natively, so `**Steve**` displays bold there.

### Room naming

- `beat:<beat _id hex>` — fields `body`, `name`, `desc`
- `character:<character _id hex>` — fields `name`, `hollywood_actor`, `fields.<each non-core template field>`
- `set:<set _id hex>` — fields `name`, `description` (sets have a fixed schema, no template)
- `dialogs:<beat _id hex>` / `video_prompts:<beat _id hex>` — per-beat dialog and Scenes-tab rooms (the last exposes `scene:<scene _id>:title` and, per cut, `item:<cut _id>:title`, `:prompt`, `:start_frame_prompt`, `:end_frame_prompt`)
- **Three project-scoped singleton rooms**: `plot:<projectId>` (fields `title`, `synopsis`, `dialogue_style`, `directorial_voice`), `notes:<projectId>` (one y-doc for all of a project's director's notes; each note's text is fragment `note:<note _id>:text`), `library:<projectId>` (library image/attachment names and descriptions)

Entity rooms are ObjectId-derived and carry no project segment — `resolveRoom` resolves (and verifies) the owning project from the entity doc itself. URLs use the human-meaningful identifier under the project prefix (`/p/<projectTitle>/beat/2` for the beat at order=2; `/p/<projectTitle>/character/Steve` for the character whose stripped name is "Steve") and the route resolver maps to the stable `_id` for the y-doc room name. Reordering beats breaks shared URLs but never shuffles y-doc state across the wrong rooms.

### Request lifecycle (`src/discord/messageHandler.js` → `src/agent/loop.js`)

1. `handleMessage` filters for the configured channel, extracts allowed image attachments (PNG/JPEG/WEBP), and serializes per-channel work through `keyedMutex` so two messages in the same channel can never interleave.
2. `loadHistoryForLlm` reads the last 60 docs from the `messages` collection and converts each to an Anthropic SDK message (`docToLlmMessage` in `src/mongo/messages.js`) — including raw `tool_use` / `tool_result` blocks. The agent therefore "remembers" prior tool calls across turns.
3. `runAgent` rebuilds the **system prompt from current Mongo state on every iteration** (`buildSystem` calls `listCharacters`, `getCharacterTemplate`, `getPlotTemplate`, `getPlot` each loop). When a tool call mutates state mid-loop, the next iteration's system prompt reflects the change — tools that update the template (e.g. `update_character_template`) rely on this.
4. The loop runs at most `MAX_TOOL_ITERATIONS = 12` Anthropic round-trips. Anything else returns a "(Agent hit max tool iterations.)" message.
5. After the assistant returns non-tool text, the user/assistant turns from this run (everything from `agentStart` onward, including tool blocks) are persisted via `recordAgentTurns` so they appear in next turn's history.

### Tool result sentinel protocol

Some tool handlers can't return their payload as JSON — they need to upload a file to Discord. The convention (`src/agent/loop.js` → `interceptAttachment`):

- `__PDF_PATH__:<absolute path>` → loop pushes path onto `attachmentPaths`, replaces the tool result with `"PDF generated and queued for upload."`.
- `__IMAGE_PATH__:<absolute path>|<note>|<gridfsId?>` → same, with the optional note becoming the tool result. The optional 3rd segment, if it parses as a 24-hex GridFS file id, is converted into a clickable `imageLink(...)` URL and pushed onto `attachmentLinks`.
- `__IMAGE_PATHS__:<paths_tab_separated>|<note>|<ids_tab_separated?>` → batch form for several images at once.
- `__ATTACHMENT_PATH__:<absolute path>|<note>|<gridfsId?>` → non-image attachments (any content type). The optional id surfaces a `/attachment/<id>` URL via the Express server.
- `__CSV_PATH__:<absolute path>|<note>` → no link (the file lives only on disk).

`sendReply` attaches every collected file to the final Discord reply, then sends one extra footer message listing all download links — PDF links derived from the filename, plus any `imageLink`/`attachmentLink` URLs collected from the sentinels. `cleanupTmpAttachments` deletes anything inside `os.tmpdir()` afterwards. **Never use these sentinels for non-tmp paths** — the cleanup pass refuses to touch files outside `os.tmpdir()`, but the assumption that `attachmentPaths` are temporary is baked in. (PDFs are the exception: they live in `config.pdf.exportDir` and are served by filename, not via the sentinel-id path.)

### Tool / handler parity

`src/agent/tools.js` is the JSON schema list sent to Anthropic; `src/agent/handlers.js` exports `HANDLERS` keyed by tool name. `tests/tools-schema.test.js` enforces a 1:1 mapping for **dispatchable** tools (every entry in TOOLS without `metaTool: true` must have a matching handler) — adding a regular tool requires adding both halves or the test fails. `dispatchTool` wraps every handler so a thrown error becomes `"Tool error (name): message"` text returned to the model rather than crashing the loop.

Each tool entry in TOOLS may carry three **internal-only** fields, stripped from the API payload by `toolDefsForApi` before send:
- `keywords: string[]` — synonyms used by the BM25-lite scorer in `src/agent/toolSearch.js`. Kept separate from `description` so the model isn't bombarded with synonym lists, but the search-by-user-language recall still works.
- `metaTool: true` — marker for loop-level meta tools (`tool_search`, `delegate_writing`) that the loop intercepts inline rather than dispatching through `HANDLERS`.
- `writerOnly: true` — the 8 creative text tools (`edit`, `load_writing_context`, `create_beat`, `create_character`, `bulk_update_character_field`, `add_director_note`, `add_film_dialogue_sample`, `update_character_template`) that, in two-tier mode, only the writer subagent may call (see Two-tier models below).

### Two-tier models: orchestrator + writer subagent

`config.anthropic.agentModel` (`ANTHROPIC_AGENT_MODEL`, default `claude-sonnet-5`) runs the agent loop; `config.anthropic.model` (default `claude-fable-5-1`) is the creative model. When they differ (**two-tier mode**), the orchestrator loses the `writerOnly` tools (excluded from its core set and from `tool_search` results) and instead gets the `delegate_writing` meta-tool: the loop intercepts it (after the review-mode gate — review mode blocks delegation) and spawns `runWriterAgent` (`src/agent/writerAgent.js`), a mini-loop on the creative model with a static tool surface (`WRITER_TOOL_NAMES`: the 8 creative tools + read/navigation tools, no `tool_search`). The writer cannot see the Discord conversation — the orchestrator's `task` brief must be self-contained (the system prompt's `# Writing & text changes` section enforces this). The writer shares the turn's `context` object, so the `load_writing_context` beat-body gate and `touchedEntities` entity links work unchanged; its final text becomes the `delegate_writing` tool result (failures come back as `Tool error (delegate_writing): ...` with `is_error`), and the loop force-rebuilds the system prompt after any delegation. The writer records its own `token_usage` doc under its model. **Escape hatch:** set `ANTHROPIC_AGENT_MODEL` equal to `ANTHROPIC_MODEL` → legacy single-model mode (`LEGACY_CORE_TOOL_NAMES`, creative tools searchable, no delegation tool). `buildSystemPrompt` takes `twoTier` and swaps the writing-workflow prompt sections; the flag is part of the stable-text memo key.

### Runtime model selection (Admin → Models)

Every Claude call resolves its model at CALL time via `modelFor(slot)` from `src/llm/modelSlots.js` — never capture `config.anthropic.model` (or a `modelFor()` result) in a module-level const, or the Admin page's change won't reach that site until a restart. Seven slots: `agent` (loop orchestrator; env fallback `ANTHROPIC_AGENT_MODEL`), `writer` (writer subagent / creative tools), `dialog`, `storyboard` (the key is historical — the planning & vision slot: image-sheet plate planners, set description, artwork critique), `critique` (beat critique/rewrite), `analysis` (`analyzeText` default) — all falling back to `ANTHROPIC_MODEL` — and `enhancer` (`ANTHROPIC_ENHANCER_MODEL`). Overrides persist in `app_settings` `{_id:'models', slots}` (`src/mongo/appSettings.js`); `loadModelOverrides()` runs at boot right after `connectMongo()`, and `PUT /api/admin/models {slots}` (admin-only, partial merge, `null` reverts) applies in-process immediately. `GET /api/admin/models` returns per-slot default/override/effective plus a catalog (static `KNOWN_MODELS` merged with a 10-min-cached `models.list()`). The two-tier check in `loop.js` is `modelFor('agent') !== modelFor('writer')`, so the Admin page can flip the loop between two-tier and single-model mode live. The SPA panel is `web/src/widgets/ModelSlotsPanel.jsx`.

### Coding-agent providers (dev only: Claude Code / Codex)

Admin → Models can point any slot at the host's logged-in **Claude Code** (`@anthropic-ai/claude-agent-sdk`) or **Codex** (`@openai/codex-sdk`) instead of the API, with a free-text model (blank = the agent's own default) and an effort level. Gated on `LLM_HARNESS_ENABLED=1` (only `docker-compose.dev.yml` sets it; `PUT /api/admin/models` answers 400 for a harness target without it, and a stored harness override on a server without the flag is ignored → API default). A harness override is stored as `{provider, model, effort}`; `modelFor()` returns an encoded id `claude-code:<model|default>:<effort|default>` / `codex:…`, and the **routing client** that `getAnthropic()` returns (`src/anthropic/client.js#createRoutingClient`) sends those ids to `src/llm/harness/` while every other id reaches the real SDK — so no call site knows. Every Claude call must go through `getAnthropic()` (never `new Anthropic(...)`) or it bypasses the router. The adapter (`translate.js`, pure) renders system + transcript (tool calls/results, images as attachments) into one prompt; tool-bearing requests answer a strict envelope `{text, tool_calls:[{name, input_json}]}` mapped back to `tool_use` blocks (`stop_reason: 'tool_use'`), `output_config` json_schema requests pass the schema through, the rest is plain text; an unmappable answer retries once with a correction. `messages.stream()` is emulated (one final `inputJson` per tool call — no incremental deltas), `countTokens` rejects (the loop skips section-token measurement). Each call is a fresh session with **full access** (Claude: `bypassPermissions`, `settingSources: ['user','project']`, `claude_code` preset + the app system prompt appended; Codex: `danger-full-access`, approvals never), capped at `LLM_HARNESS_CONCURRENCY` (3) concurrent CLI processes. The child env strips `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` so the mounted subscription logins are used, not the bot's API key. Usage rows record the encoded model plus `meta.cost_usd` (Claude's estimate). **Dev container**: runs as `node` (uid 1000 = host user) with `HOME=$HOME`, and mounts `~/.claude`, `~/.claude.json`, `~/.codex` at the same absolute paths (the plugin registry stores absolute paths) — sessions land in the host history owned by the host user; host hooks/MCP servers that need host-only binaries just fail inside the container. Live check: `LLM_HARNESS_ENABLED=1 node scripts/harness-smoke.js [claude-code|codex] [model] [effort]` (text, tool and schema calls). Test seam: `_setHarnessRunnersForTests`. Both agent SDKs are **devDependencies** (~650 MB of bundled CLIs; the prod image's `npm ci --omit=dev` skips them and they are only reached through dynamic imports behind the flag). The Agent SDK needed `@anthropic-ai/sdk >= 0.93`, so the next prod deploy is `./deploy.sh --rebuild`.

### Lazy tool loading via `tool_search`

The full tool registry is ~80+ tools. To keep the per-request input small and keep the model focused, the loop only sends a small **core set** in the `tools` parameter on each iteration; everything else is loaded on demand.

- `src/agent/tools.js` exports `CORE_TOOL_NAMES` (a Set of 9, two-tier mode) — `tool_search`, `get_overview`, `list_characters`, `list_beats`, `get_plot`, `get_current_beat`, `search_message_history`, `screenplay_search`, `delegate_writing` — and `LEGACY_CORE_TOOL_NAMES` (single-model mode: swaps `delegate_writing` for `edit` + `load_writing_context`). The loop seeds from one or the other based on the two-tier check.
- The model expands the loaded set by calling `tool_search({ query, limit? })`. The loop intercepts that call (it is `metaTool: true`, has no entry in `HANDLERS`), runs `searchTools(query)` from `src/agent/toolSearch.js`, and adds the matched names to a per-turn `loadedToolNames` Set. The next iteration's `tools` parameter is rebuilt from that set.
- `loadedToolNames` is per-turn (re-initialized on each `runAgent` call). Across-turn re-search is fine — historical `tool_use` blocks in the message array don't need to be in the current `tools` parameter; the API only validates current-turn tool calls.
- The system prompt's `# Tool loading` section instructs the model on this protocol; the prompt also still mentions specific tool names throughout (the model uses those names as search seeds).
- `src/agent/toolSearch.js` is BM25-lite over name (×3) + keywords (×2) + description (×1), with prefix matching so plurals/tenses still hit. `searchTools(query, { limit, minScore, exclude })` returns matched tool names. Adjust scoring there, not in the loop.
- `withToolsCache` in `src/agent/loop.js` puts the standard ephemeral `cache_control` breakpoint on the **last** entry of whatever tools array is currently loaded. When a `tool_search` adds new tools mid-turn the breakpoint moves, so cross-iteration tools-section caching is best-effort — the system prompt has its own independent `cache_control` markers that aren't affected.

### MongoDB layout (`src/mongo/`)

- `characters` — one doc per character, stamped with `project_id`. Custom template fields live under `fields.{...}`; core fields (`name`, `plays_self`, `hollywood_actor`, `own_voice`) are top-level. `(project_id, name_lower)` has a compound unique index — the same name can exist in two projects. `getCharacter(projectId, idOrName)` accepts either a 24-char hex `_id` (verified against `project_id`; cross-project ids behave as not-found) or a case-insensitive name.
- **Wardrobe lock** (`src/web/wardrobe.js`, pure; 2026-10-02). ### Scenes tab (beat → scenes → cuts → frames → video)

The `Scenes` beat tab (`/p/<title>/scenes/<order>`) is the ONLY beat → video path, and it is hand-driven: nothing is planned, picked, checked or scored for the user. It replaced the planner-driven Prompts tab on 2026-10-04 (see "Retired: Prompts tab" below); `/prompts*` and `/storyboard*` redirect to it.

- **Model.** A beat has **scenes** (a number — `order` — and a name) and each scene has **cuts**, labelled `<scene order>.<cut_index>` ("2.3"; the label is derived, never stored). A cut has a name, a duration (0.5 s steps), a **video prompt**, a **start frame** and an **end frame** — each frame with its own prompt, its own ordered reference images and its rendered image — and the generated clip. Cuts are only ever created inside a scene.
- **Data.** `video_scenes` (`src/mongo/videoScenes.js`): `{project_id, beat_id, order, title}`. `video_prompts` rows are the cuts (`src/mongo/videoPrompts.js`): `{project_id, beat_id, scene_id, cut_index, order (beat-wide, `recomputeCutOrderForBeat`), title, prompt, duration_seconds, start_frame, end_frame, video_* (file, duration, model, provider, params, cost, `video_comfy`)}`; a frame is `{image_id, prompt, reference_ids[] (≤ `MAX_REFERENCE_IMAGES` = 9), model, generated_at, previous_image_id}`. The collection and room names are kept from the old tab so the beat-delete and project-delete cascades, permissions and indexes are unchanged. Rows written by the old planner still load (unknown fields are ignored by `backfill`); `scripts/wipe-scenes.js (--project "Title" | --all-projects) [--apply]` deletes every scene and cut with their frames and clips (dry run by default; `mongodump` first).
- **Text is collaborative.** Room `video_prompts:<beatId>`: fragment `scene:<id>:title` and, per cut, `item:<id>:title`, `item:<id>:prompt`, `item:<id>:start_frame_prompt`, `item:<id>:end_frame_prompt` (the last two persist to `start_frame.prompt` / `end_frame.prompt`). There is no REST route for any of them. Duration, reference lists, images and clips are scalar Mongo fields written through the gateway, which pings the room (`fields_updated`) so open pages refetch. `createVideoSceneViaGateway` and `createVideoPromptViaGateway` seed every fragment of the new row BEFORE the insert (`seedNewRowFragments`).
- **Routes** (`src/web/cutRoutes.js`): `GET /video-scenes?beat_id=` → `{beat, scenes:[{…, cuts}]}`; `POST /video-scene {beat_id, title?}` (201), `DELETE /video-scene/:id` (its cuts and their media go too; scenes and cuts renumber), `DELETE /video-scenes?beat_id=` (every scene of the beat with every cut, frame and clip — the toolbar's **Delete all scenes** button, behind a confirm; `deleteAllVideoScenesViaGateway`), `POST /video-scenes/reorder {beat_id, ordered_ids}`; `POST /cut {scene_id}` (201), `PATCH /cut/:id {duration_seconds}`, `DELETE /cut/:id`, `POST /cuts/reorder {scene_id, ordered_ids}`; per frame (`start` | `end`): `POST /cut/:id/<frame>-frame/generate {image_model?, comfy_params?}` (202 `{job_id}`; 400 no prompt; 409 `CUT_BUSY`), `PATCH /cut/:id/<frame>-frame {reference_ids}`, `DELETE /cut/:id/<frame>-frame` (image + undo blob; prompt and references kept), `POST /cut/:id/<frame>-frame/undo`; `GET /cuts/frames/job/:jobId`; `GET /cuts/jobs?beat_id=` → `{frames, comfy_videos}` (what a reopened page reattaches to). `src/web/cutVideoRoutes.js`: `GET /cuts/candidates?beat_id=` (the artwork catalog the reference picker offers), `POST /cut/:id/fal-video/preview|generate`, `GET /cut/:id/video-job/:jobId` + pre-auth SSE `/events` (ComfyUI registry first, then fal), `DELETE /cut/:id/video`. ComfyUI: `POST /api/cut/:id/video/preview|generate`, `POST /cut/:id/video/job/:jobId/cancel` (`src/web/comfyRoutes.js`).
- **Rendering a frame** (`src/web/cutFrames.js`): the frame's prompt + EXACTLY the frame's `reference_ids` (capped at `maxReferenceImagesFor(model)`; an empty list renders from the prompt alone — nothing is auto-picked) → `composeStartFramePrompt` binds each reference by what it is, **in the stored order** (2026-10-05: `orderReferencesByRole` was removed — the preamble numbers the references `Image 1…` in list order, so a frame prompt written against `reference_ids` can name the Nth id as `Image N`; authors list identities first, set plates after, the start frame last), read from `buildReferenceCatalog`: character artwork = `identity`, a wardrobe plate = `wardrobe`, set artwork = `look`, and — for the END frame — the cut's own start-frame image = `continuity` (the SPA's "+ Start frame" button adds it; `repointStartFrameReference` keeps that id current when the start frame is re-rendered or undone). Without the binding preamble multi-reference models treat image 1 as the canvas. ComfyUI image models (`comfy:<id>`) write their own binding. → `dispatchStillImage` (`src/web/stillImageDispatch.js`) → a beat-owned GridFS image → `setVideoPromptStartFrameViaGateway` (the replaced image becomes the one-step undo target). Jobs are in-memory, one per cut+frame (`CUT_BUSY` 409), with NO beat lock — a cut's two frames and different cuts render side by side. Seams: `_setCutFrameDispatcherForTests`, `_resetCutFrameJobsForTests`.
- **Generating the video.** The SPA enables Generate video only when both frames have an image. Either provider gets the cut's video prompt as written (`assembleCutPrompt` — or a one-off override typed in the dialog), the start frame and the end frame; the length defaults to the cut's duration snapped to what the model renders (`snapDurationUp` for ComfyUI, `pickDurationSeconds` for fal). **fal.ai** (`src/web/falVideoGenerate.js`, owner `{kind:'video_prompt', id}`): one render per cut at a time (`VideoCutBusyError` → 409 `CUT_BUSY`), other cuts in parallel. **ComfyUI** (`src/web/comfyVideoGenerate.js`): one job per cut on the one-GPU `enqueue` queue (shared with ComfyUI stills), `queue_position`, cancel while queued. A cut carries no reference images and no dialogue recording, so reference-to-video and lip-sync models are refused (`MissingReferenceImagesError` / `InvalidComfyParamsError`; the dialogs say so). The previous clip is deleted when a new one lands.
- **Whole-beat buttons** (2026-10-04; toolbar on top of the beat's Scenes page, routes in `src/web/cutBatchRoutes.js`). **Generate all videos…** opens `GenerateAllVideosDialog.jsx` (ComfyUI | fal.ai tabs reusing `ModelGroup`/`ParamField` and the fal `ModelPicker`; "skip cuts that already have a video", default on) → `POST /cuts/videos/generate-all {beat_id, provider: 'comfy'|'fal', model_id, skip_existing?, params?, confirm_spend?, resolution?, fps?, generate_audio?}` (202 `{batch}`; 409 `BATCH_BUSY`; the first eligible cut is preflighted so a bad model / unconfigured provider is a 4xx/503 before anything is queued) and closes. `src/web/cutVideoBatch.js` is the runner: one in-memory batch per beat (a restart ends it), every cut with both frames and a prompt in page order, each through the SAME per-cut job the single buttons start (`startComfyCutVideoJob` / `startVideoGenerationJob`; ComfyUI 1 at a time, fal 2), each cut's own prompt and length, no per-render overrides; the cut is re-read right before its turn (deleted / lost a frame → `skipped`), a `CUT_BUSY` cut is followed instead of failed, a failed cut is recorded and the batch carries on. `GET /cuts/videos/batch?beat_id=` (polled every 4 s by `widgets/cutVideoBatch.jsx`, also the reattach path) → items `{cut_id, label, status: queued|running|done|error|skipped|cancelled, reason, error, job_id}` + `counts`; `POST /cuts/videos/batch/cancel {beat_id}` stops before the cuts still waiting. SPA: `CutBatchBanner` (progress, Stop batch, final tally + Dismiss) and on each cut `CutBatchStatus` + a spinner in the cut header while it renders. Seams: `_setCutBatchProvidersForTests`, `_resetCutBatchesForTests`. **Download all videos** → `POST /cuts/videos/download {beat_id}` (202 `{job}`; 400 when no cut has a clip; cuts without one are left out and listed in `job.missing`), poll `GET /cuts/videos/download/:jobId`, then `GET …/:jobId/file` via `apiDownload`. `src/web/cutVideoJoin.js`: every clip normalized by ffmpeg to the FIRST clip's size and frame rate (letterboxed, H.264/AAC, silent clips get a silent track), then the concat demuxer joins them — straight cuts, page order. Nothing is stored: the MP4 is a tmp file kept for an hour with its job. Seam: `_setJoinSpawnImplForTests`. Tests: `tests/cut-video-batch.test.js` (one case runs real ffmpeg when it is on PATH).
- **ComfyUI provider** (`src/comfy/*`, dev-only — production never sets `COMFYUI_URL`, so the SPA says "ComfyUI rendering is disabled on this server" and fal.ai stays available). The bot spawns the `comfy-mcp` stdio server (`COMFY_MCP_COMMAND`, `COMFY_BIN`) which talks to the ComfyUI at `COMFYUI_URL`. `COMFY_VIDEO_MODELS` (`src/comfy/videoModels.js`) maps a registry id to a ComfyUI template + slot addresses + param schema (image slot roles `start_frame` | `end_frame` | `reference`); models can also be registered from the gallery (Admin → ComfyUI templates: `src/comfy/templateMap.js#autoMapTemplate`, `app_settings {_id:'comfy_models'}`, `GET|PUT|DELETE /api/admin/comfy/models[/:id]`). `paramMap.js` validates params and builds `set_workflow_slot` overrides. ### MCP server for coding agents (`src/mcp/`, 2026-10-04)

A third listener in the bot process (`MCP_PORT`, default 3002, `0` = off; `startMcpServer()` after Hocuspocus in `src/index.js`): streamable HTTP at `/mcp`, **no auth**, so a command-line agent (Claude Code, Codex) can plan a beat's Scenes tab itself. Storage only — no model call, no rendering. It is in-process because every write goes through the mutation gateway (open pages update live). Install: `claude mcp add --transport http screenplay http://localhost:3002/mcp` / `codex mcp add screenplay --url http://localhost:3002/mcp`.

- **Stateless**: `server.js` builds a fresh `McpServer` + `StreamableHTTPServerTransport({sessionIdGenerator: undefined})` per POST; GET/DELETE `/mcp` answer 405. Safety is the network: compose publishes `127.0.0.1:${MCP_PORT}` only and `hostHeaderValidation` refuses a `Host` outside `MCP_ALLOWED_HOSTS` (default localhost; `*` = any) — the DNS-rebinding guard that keeps a web page from driving it.
- **Tools** (`tools.js`; a thrown error becomes `isError` text): read — `list_projects`, `get_story`, `list_beats`, `get_beat` (body in page form via `hardBreaksToLines`, + dialogue), `get_dialogue` (read-only), `get_cast`, `list_characters`, `list_sets`, `list_artwork` (EVERY picture of one character or set, uncapped: done artworks then gallery uploads, `roles` portrait / main / wardrobe_plate), `list_reference_images` (the beat's `buildReferenceCatalog`), `get_scenes`, `view_image` (JPEG image content, `max_px` default 1024); write — `create_scene` (optional `cuts[]` = a whole scene in one call; every cut is validated before anything is written), `update_scene`, `delete_scene`, `reorder_scenes`, `create_cut`, `update_cut`, `delete_cut`, `reorder_cuts`, `set_frame_image` (`image_url`, or `image_id` = a COPY — a frame owns and deletes its picture), `clear_frame_image`, `undo_frame_image`, `set_cut_video` (URL), `clear_cut_video`.
- **Addressing** (`resolve.js`): beat tools take `project` (title or id; default project when omitted; unknown → error, checked BEFORE `getPlot`, which would create a plot) and `beat` (order / id / name). Scene and cut tools take the id alone — the row's `project_id` names the project. Reference ids must be existing images of that project.
- **Files never travel as tool arguments** (base64 in a tool call is megabytes of tokens): `PUT|POST /upload?cut_id=&target=start_frame|end_frame|video` with the raw file as the body (`curl -T`). The server's `instructions` carry the upload URL (`MCP_PUBLIC_URL`, else the request's Host).
- **Write order** (`store.js#updateCut`): scalars (duration, reference lists, position) first, text fragments last, and the answer overlays the text just written — a frame write carries the frame's stored prompt, and with Hocuspocus running a text write reaches Mongo a moment after the call.
- Shared with the Scenes tab: `storeCutFrameImage` (cutFrames.js — the tail of `renderCutFrame`; a frame set over MCP is refused while the tab renders that frame, `activeCutFrameJob`) and `src/web/cutValidation.js` (`cleanIdList`, `isValidCutDuration`, `MAX_SCENE_TITLE`). An uploaded clip is stored with `video_provider: 'fal'` and the caller's `model` as its label.
- Tests: `tests/mcp-server.test.js` (tools through the SDK's `InMemoryTransport`, the upload endpoint and real streamable HTTP on port 0).

### Beat critique (writing + artwork)

The beat page's Critique tab (`web/src/widgets/CritiqueTab.jsx`) is a two-section accordion (`CritiqueSection.jsx`, native `<details>`).

- **Writing critique** (`src/web/critiqueFacets.js` → `critiqueGenerate.js`, storage `src/mongo/critiques.js` at `plots.beats[].critique`, `version: 2`). Seven facets (`format` and `direction` are `required` and weigh 1.5; the rest 1), each with 3-4 named **criteria** (a criterion may carry its own `weight`; `staging` is 0.5) carrying written 3/6/9 **anchors**; `buildFacetSystemPrompt` renders `SCORING_RULES` + focus + the criteria table. One `output_config` json_schema call per facet (`facetOutputSchema`; the schema's criterion keys are an enum) returns `criteria[{key, applicable, score, evidence[{quote, note}], rationale, to_raise}]` (`to_raise`, 2026-10-03: how to fix THAT criterion in this beat — required by scoring rule 11 for every applicable criterion under 10, blanked by the normalizer at 10 / n/a; shown as **To fix:** on the rubric row; `formatTargets` in beatRewrite.js hands each criterion's `Why N:` rationale and `To raise it:` line to the strategist, the rewriter and the edit planner). **Pacing is rhythm, not brevity** (2026-10-03): the pacing critic's every fix was a cut, and a climb left beats as a rushed summary of themselves. Its focus now says a slow stretch is fixed by ADDING (a want with an obstacle, a complication, behaviour, anticipation — the lines written out), a cut is recommended only for text weak in itself (awkward, played twice, explaining what was shown) and never a whole sequence, and a thin/rushed beat is a fault; the anchors score rushed entries, unbuilt turns and a too-thin beat at 6 or below). **Keep list is not a veto** (2026-10-03): `formatKeepList` drops any praised quote an issue also quotes, and `KEEP_RULE` (all three rewrite prompts) says an issue's fix or a target outranks it — a keep list that outranked them made the planner refuse every "replace/cut this sequence" fix; `FIXED_FACTS_RULE` adds that leaving a detail out is not contradicting a document, and the edit planner cuts a multi-paragraph run with one edit per paragraph, `issues[{severity: must_fix|should_fix|nit, criterion, quote, problem, fix}]`, `strengths`, `summary`. ### Optional integrations

- `src/gemini/client.js` — Nano Banana image generation (`gemini-2.5-flash-image`). If `GEMINI_API_KEY` is unset, the `generate_image` handler returns a friendly error string; the rest of the bot keeps working.
- `src/tmdb/client.js` — TMDB v4 read-only. Same pattern: `tmdb_*` tools short-circuit with an error when `TMDB_READ_ACCESS_TOKEN` is missing. `tmdb_show_image` only accepts URLs on `image.tmdb.org` (enforced by `isTmdbImageUrl`).
- `src/eleven/client.js` — ElevenLabs REST (raw fetch, no SDK). If `ELEVEN_LABS_KEY` is unset, `/api/eleven/*` endpoints report unconfigured/503 and the SPA's ElevenLabs playground tab disables itself. Voice collection is per-project in `eleven_voices` (voice docs track `added_to_account`; shared-library voices are lazily added to the ElevenLabs account on first TTS/STS use). Outputs persist as GridFS attachments with `owner_type: 'playground'`, `generated_by: 'elevenlabs/<tool>'`.

When adding a new optional integration, follow this pattern (return user-facing error string, don't throw) so a missing API key doesn't break the agent loop.

### Image validation (`src/mongo/imageBytes.js`)

`fetchImageFromUrl` enforces: HTTP(S) only, `<= 25 MB`, content type in `{image/png, image/jpeg, image/webp}`, **and** sniffed magic bytes must match the declared/picked content type. Don't bypass this when adding new image entry points — `validateImageBuffer` is the equivalent for in-memory bytes (e.g. Gemini output).

const fakeDb = createFakeDb();
